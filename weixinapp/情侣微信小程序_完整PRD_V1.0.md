# 情侣微信小程序《两个人的小世界》完整 PRD

**版本：** V1.0  
**项目阶段：** 个人情侣专属工具 / 双人使用 / 不公开上线  
**平台：** 微信小程序  
**文档依据：** 首页、同步心情、好好吃饭、日常、计划共 5 张现有高保真页面  

---

## 1. 产品概述

### 1.1 产品定位

这是一个只属于两个人的情侣微信小程序，用一个温暖、手绘、像恋爱手账一样的空间，把两个人每天的状态、吃饭、回忆和约会计划放在一起。

核心目标不是做功能很多的“情侣工具箱”，而是形成一个非常轻的日常陪伴闭环：

> 打开小程序 → 看见 TA → 关心 TA → 和 TA 互动 → 记录今天 → 期待下一次见面

### 1.2 核心价值

1. **看见彼此**：恋爱天数、城市、天气、状态等轻信息。
2. **表达关心**：同步心情、一键想你、提醒吃饭、叫醒服务。
3. **共同生活**：约饭、共同计划、纪念日、约会。
4. **留下回忆**：日常动态、照片、评论、点赞。

### 1.3 产品关键词

手绘、温暖、治愈、情侣、生活感、轻互动、低压力、私人空间。

---

# 2. 用户与产品边界

## 2.1 用户范围

本产品只服务一对情侣，因此产品模型不是“社交平台”，而是一个 **1 对 1 私密空间**。

### 核心角色

- 用户 A：本人
- 用户 B：伴侣
- Couple：两人的情侣空间

## 2.2 与公开产品最大的区别

不需要：

- 搜索其他用户
- 关注关系
- 公域推荐
- 群聊
- 公开评论
- 内容审核体系
- 复杂推荐算法
- 商业化系统

这样可以大幅降低开发复杂度，把精力集中在体验与视觉上。

# 4. 全局视觉与交互规范

## 4.1 视觉基准

完全沿用现有 5 张页面风格：

- 暖米白纸张背景
- 水彩/彩铅纹理
- 手写风标题
- 圆角纸片卡片
- 低饱和粉、蓝、绿、橙作为功能色
- 花草、爱心、太阳、猫咪等小装饰
- 情侣角色作为品牌 IP
- 页面整体有“恋爱手账”感觉

## 4.2 UI 原则

### 卡片

- 大圆角
- 细手绘边框
- 内部留白充足
- 每个功能卡片只承担一个核心任务

### 按钮

主要按钮以珊瑚粉/蜜桃色为主。

文案尽量使用：

- 提醒 TA
- 去分享
- 添加约会
- 确定选择
- 想你了

避免：

- 提交
- 保存数据
- 确定

## 4.3 动效

动效只做轻量反馈，不做复杂转场。

典型动效：

- 点心情 → 卡片轻微弹跳
- 想你 → 爱心飞出
- 点赞 → 爱心缩放
- 提醒吃饭 → 铃铛摇晃
- 创建约会 → 小爱心飘出
- 日历切换月份 → 轻微滑动

# 5. 全局交互规范

## 5.1 点击反馈

所有可点击卡片必须有反馈：

- 轻微缩放
- 阴影变化
- 边框高亮

点击后立即有视觉反馈，避免用户误以为没有响应。

## 5.2 Loading

统一使用：

> 小太阳/小爱心轻微旋转或跳动

避免系统默认转圈破坏视觉风格。

## 5.3 空状态

统一使用情侣插画 + 轻文案。

例如：

> 还没有记录哦
> 一起写下今天的第一件小事吧 ❤️

## 5.4 错误状态

避免技术错误提示。

例如不要直接展示：

> request:fail

统一转换成：

> 好像走神了一下，再试一次吧～

# 7. 同步心情 PRD

> 参考现有心情选择高保真稿。

## 7.1 页面目标

让用户用 1 次点击表达今天的状态，并同步给伴侣。

## 7.2 心情选项

沿用现有 9 个视觉卡：

```text

悲伤
愤怒
害怕
喜欢
平静
乐观
兴奋

```

## 7.3 交互流程

```text
进入心情页
↓
选择一个心情
↓
选中卡片高亮
↓
点击“确定选择”
↓
保存今日心情
↓
同步给 TA
↓
返回上一页/首页
```

## 7.4 单选规则

一天只保留 1 个“当前心情”。

如果当天重复修改：

> 直接覆盖今日心情，不产生多条首页状态。

历史记录可以保留修改轨迹，也可以只保留最终状态；MVP 建议只保留最终状态，降低数据复杂度。

## 7.5 伴侣侧反馈

TA 收到后可以看到：

> 林舟今天的心情：悲伤 🥺

提供轻互动：

- 抱抱 TA
- 我在哦
- 我也想你

## 10.3 创建餐食分享

点击“去分享”：

- 选择图片 1～9 张
- 填写一句话
- 点击发送


# 18. 首页与四大 Tab 的数据联动

这是产品体验中很重要的一层。

### 心情

心情页更新 → 首页同步显示。

### 约饭

好好吃饭创建约饭 → 计划自动出现一条“约饭”事件。

### 餐食分享

好好吃饭发布 → 同步到日常动态。

### 约会

计划创建 → 月历标记 + 约会卡片更新。

因此 4 个 Tab 不是 4 个孤立功能，而是一个共同的数据空间。

# 21. MVP 技术范围

由于产品只有两个人使用，建议不要做过度架构。

推荐采用：

- 微信小程序前端
- 轻量后端/云开发
- 云数据库
- 云存储保存图片
- 简单 API

核心要求是：

**数据可靠、图片稳定、双人同步简单。**

不需要微服务、消息队列、复杂缓存等大型架构。

# 24. 关键业务规则

## 24.1 数据私密性

所有内容默认只对情侣双方可见。

## 24.2 删除

只有创建者可删除自己的内容。

## 24.3 双人状态

涉及 TA 的展示，都必须区分：

- 当前状态
- 最后更新时间

避免过时信息被误认为实时信息。

## 24.4 时间

所有日期时间统一使用用户所在时区进行展示；本项目只有两人使用时，可直接按双方实际所在地处理，但数据层仍建议保存标准时间戳。

# 25. 隐私与位置设计

位置是可选功能。

用户可以选择：

```text
允许 TA 查看我的城市
允许 TA 查看两人距离
```

不要默认公开精确经纬度。

展示层默认只显示城市，例如：

> 上海市 · 1小时前

# 29. 产品体验重点

这个产品最终最重要的不是“功能全不全”，而是以下三个感觉：

### 1. 打开就能看到 TA

首页必须始终围绕“我们两个人”展开。

### 2. 每一次点击都带一点感情

不要出现太多冷冰冰的系统文案。

例如：

> 已创建

改为：

> 好啦，约定完成 ❤️

### 3. 功能之间要自然流动

吃饭 → 日常  
约饭 → 计划  
心情 → 首页  
想你 → 通知  
约会 → 日历

让整个小程序像一个完整的情侣生活空间，而不是 4 个工具页面。

# 30. 最终产品定义

> **《两个人的小世界》是一款只属于一对情侣的微信小程序。它不追求复杂功能，而是用“心情、吃饭、日常、计划”四个非常简单的入口，把两个人每天的状态、关心和未来的期待轻轻地放在一起。**

最终形成一个完整的情侣日常闭环：

```text
      今天的我
          ↓
      同步心情
          ↓
      关心 TA
          ↓
      好好吃饭
          ↓
       记录日常
          ↓
       计划见面
          ↓
     期待下一次见面
          ↓
       再回到首页
```

这就是这个小程序最核心的产品体验。
